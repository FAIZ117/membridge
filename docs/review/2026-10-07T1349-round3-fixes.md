## 4. C20: why the exchange-based wake was reverted

The round-3 performance pass (Q4) suggested `Atomics.exchange(flag, 0)` in
the notifier so a full ring costs one wake per park. I implemented it, and the
new full-ring test failed intermittently: a 250 ms stall in 2–5 of 8 × 20k
messages, with sync **and** async producers. In-place instrumentation of
`dist/src/ringbuffer.js` showed the consumer timing out on a **full** ring
with its flag already 0. The interleaving:

1. Producer stores `HEAD` for message 1. Its exchange has not run yet.
2. Consumer reads and releases message 1, finds the ring empty, sets its flag,
   re-checks `HEAD` (unchanged) and parks.
3. The producer's late exchange for message 1 now consumes the consumer's NEW
   flag and its wake lands before the consumer is asleep.
4. Producer commits message 2, sees flag 0, and wakes nobody. The consumer
   sleeps a full slice.

A/B on the same build: a plain load gave **0 stalls in 8 rounds**, the
exchange gave 2–5. The flag check stays a plain load, and only the waiter
clears its own flag. Documented in ADR 0006 (amendment), PLAN §8.1, and the
`wakeConsumer`/`wakeProducer` comments. The accepted cost is about one extra
wake per release while the peer is parked.

## 5. Test-harness bug fixed (pre-existing, round 2)

`hardening.test.ts` "R2: concurrent create/join…" attached the creator's
`'exit'` listener only after the joiners finished. If the creator had already
exited, the event was missed and **the suite hung** — about 1 in 8 runs here.
The faster create path made it more likely. Running the same scenario outside
the runner for 30 rounds never hung, which confirms the library was not at
fault. All exit promises are now taken at spawn time. The two other
`on('exit')` waits in the suite attach in the same tick as `kill()` and are
safe.
