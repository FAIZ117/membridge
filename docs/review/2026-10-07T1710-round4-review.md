## 1. Verdict

**The round-3 core holds.** The edge-case pass ran ~1.6 M mutex acquisitions
with ~500 SIGKILLs and worker terminations mid-hold, 15 dead-slot reclaim
rounds, 380 claimer kills and chaotic ring role races: **0 overlaps, 0
deadlocks, 0 lost unlocks, 0 dual producers/consumers, 0 torn messages.** The
security pass found **no path where shared memory steers native code outside
the mapping**. The performance pass found **every hot path at parity** with
`248f731` and confirmed the round-3 gains (C6 stalls gone, C22 −30%).

**Not yet publishable.** Four correctness bugs sit at the edges of the new
APIs and the init protocol, all reproduced through the public API:

| ID | Sev | One line |
|---|---|---|
| E4-1 | P1 | `Mutex.close()` while `lockAsync` is pending: the closed instance still acquires — overlap, or a permanently wedged lock |
| E4-2 | P1 | Two concurrent `reserveAsync` on one producer get the same region — one message silently lost, the other delivered with the wrong length; C24 interning makes this easy |
| E4-3 | P2 | `tryLock` never reports `ownerDied`; the stale flag is reported to an unrelated later `lock()` (2048/2051 in a repro) |
| E4-4 | P1 | A sized joiner takes over while a live creator is in `posix_fallocate`: the creator gets `E_SIZE_MISMATCH` on its own create and the header is left at the joiner's size (5/5 at the default cap under modest CPU contention) |

Plus, small and worth doing before v0.1: S4-1 (one truncated segment freezes
every async wait in the process), S4-2/S4-5/S4-7 (`/dev/shm` FIFO hangs,
symlink aborts `reap()`, fd leaks), the pid-namespace gap in the Claiming
word (S4-3 = E4-6), and the claim-path scalability regressions (P4-1, P4-3,
P4-4).

## 3. Security pass (S4-1 … S4-15)

**Verdict:** no P0/P1. Effective boundary weaker than documented in three ways:
any local user (not only same-uid) can hang `list()`/`reap()` with a FIFO or
abort a `reap()` scan with a symlink; a peer of ONE segment can freeze every
async wait in the process; the Claiming word carries no pid namespace.

## 5. Performance pass (P4-1 … P4-10)

**Verdict:** no blockers; hot paths at parity; regressions are confined to
claim/registry costs that scale with mappings per process (invisible under
~300, hundreds of µs per claim and seconds of teardown at 10k).

| Metric | 248f731 | 46e8e02 |
|---|---|---|
| lock+unlock, P-core, 2M loop | 47.9–48.6 ns | 48.4–48.7 ns |
| tryLock+unlock | 38.9–39.1 ns | 39.1–39.5 ns |
| Contended sync 5 µs/0, 3/6/8 procs (median acq/s) | 163k / 161k / 158k | 162k / 160k / 155k |
| Waits ≥ 250 ms (108 runs per build) | 0 | 0 |
| Worst `reserveAsync`, 8 × 20k into 4 KiB | 21/24 rounds ≥ 250 ms | 0.44–3.78 ms |
| open() hot reuse | 3.26–3.80 µs | 2.09–2.68 µs |
| First-lock claim at 1k / 10k live mappings (p50) | 5.3–5.7 / 5.6–6.7 µs | 21–34 / 241–333 µs (**P4-1**) |
| Teardown of 10k / 20k collected unlinked mappings | 42–46 / 86–101 ms | 760–790 / 3060–3100 ms (**P4-2**) |
| Cold create after 10k churn (mean) | 14.7–16.7 µs | 20.5–22.2 µs (**P4-3**) |
| Unrelated claim during a stuck role settle | 0 ms | 100.3–100.6 ms (**P4-4**) |
| 32 threads claiming own segments | 563–617k claims/s | 296–341k (**P4-5**) |
| GC release of 20k un-closed instances | 1.31–1.36 s, slot stays Active | 19–25 ms, slot freed |

**Findings by severity:**
- **Medium:** P4-1 (claim scans every live mapping), P4-2 (O(n²) teardown).
- **Low–Medium:** P4-3 (O(n) prune per `Put`), P4-4 (settle sleep under `g_claim_mu`).
- **Low:**
  - P4-5: process-wide claim lock.
  - P4-6: futile wakes on a full ring; the ticket flag is the safe fix, and the exchange variant was re-tested and stalled 241–248 ms, confirming the C20 revert.
  - P4-7: +5–7% JS per ring message.
  - P4-10: `liveProducers` never drops collected entries.
- **macOS, by reading:** P4-8 (every wake is a wake-all).
- **Doc:** P4-9 (the 191-wait budget only holds on Linux ≥ 5.16).

**benchmarks.md corrections:**
- Async row: 0.44–3.78 ms worst, not 0.4–0.9.
- 64 KiB: up to 38k msgs/s and 2.49 GB/s.
- Handoff: ~155–170k/s.
- Machine line: 14-core hybrid, 18 threads; single-thread results are bimodal between P- and E-cores.
- Ring rows use a worker-thread producer.
